# Recovery and operating limits

Normal operation needs only the UI. Failed preflight checks send no mutation and leave the proposal pending; refresh proposals to replace outdated evidence. After a request may have reached CRM, the proposal becomes recovery_required. A process crash can leave applying. Both states block new approvals across processes.

Do not reset the database, blindly retry POST, or mark an item applied just to clear the queue. Preserve the database, including WAL files, or use SQLite's backup API while the app is stopped.

1. Stop the review server and daily job. Inspect the proposal's events and operations in SQLite (or the Audit trail). `intent` means the call might or might not have committed; `response` means a response was captured but verification may be incomplete; `verified` means read-back passed.
2. Use GET /api/v1/accounts and GET /api/v1/accounts/{id} with CRM_API_TOKEN. For uncertain creates, search notes for `Reconciliation reference: <full proposal fingerprint>` in the full inventory. This marker is deterministic and is stored in the original create intent. Do not send another POST if any candidate exists or the inventory cannot be read completely.
3. For CHOW: verify the successor's parent, address, name and marker, and compare every old business field against the saved current snapshot. If the old pointer already targets the verified successor, no write is needed. If the successor exists but the pointer is blank and the old snapshot remains unchanged, the only remaining operation is PATCH old.chow_current_account to the verified successor ID. **A human must explicitly approve that recovery write after seeing both records.** Do not re-parent or edit other old fields. If evidence or balances changed, stop for investigation.
4. For an uncertain single PATCH, compare all intended and preserved fields against the current account. If it already matches, no repeat write is required. If not, a human must review a freshly computed correction; do not infer success from the HTTP status alone.
5. After manual investigation/recovery, a maintainer may record a named recovery event and transition the stuck proposal with `Store.transition(id, {"recovery_required", "applying"}, "applied", "manual_recovery_verified", {"reviewer": ..., "rationale": ..., "verified_account_ids": ...})` only after confirming all effects. This is a local audit repair, not a CRM write. If no effect occurred and the decision is abandoned, use `rejected` with a clear rationale instead. Rerun reconciliation before resuming reviews.

The app intentionally does not offer an automatic recovery button or retry loop. An ambiguous timeout cannot be made safe merely by resending the request. This is a prototype limitation, documented instead of hidden.

The UI binds only to 127.0.0.1, checks allowed Host headers and requires a per-process review nonce for POSTs. It has no user identity provider or role system; do not expose it publicly. SQLite events are append-only through the application, not tamper-proof against the database owner. There is no distributed transaction or documented CRM ETag compare-and-swap. External writers can still change state in the read/write gap; run one reviewer and retain the audit.
